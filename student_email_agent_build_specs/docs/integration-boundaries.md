# Integration and data boundaries

## Runtime and access

- One local app instance serves one user and one Gmail account at a time for the first build. The browser talks only to the loopback backend; provider keys and OAuth tokens stay server-side in ignored local storage. Disconnect removes local credentials, clears current batch registrations, requests sort cancellation, and attempts token revocation. Saved account-scoped review records remain. Existing in-flight requests may finish; the app does not undo completed labels or sends.
- The app retrieves metadata for only the 15 newest inbox messages without body-derived snippets. Older-page cursors are not accepted. The **Open & sort live inbox** action fetches bounded plain text and any snippet for those messages and initiates sorting without a second confirmation. There is no separate inbox-preview panel. Connection alone reads no inbox. Sorting begins only when the user clicks Open & sort live inbox, never on a timer. Individual failed metadata records are excluded from sorting eligibility. The app stores Gmail message/thread IDs, app-owned label state, pending review decisions, draft revisions, and send-operation state; it does not create a second full mailbox archive.
- Sorting sends sender display/address, subject, date, snippet, and a bounded plain-text body excerpt for the newest displayed messages to the chosen sorting provider. Sorting body excerpts are limited to 2,000 characters and snippets to 180 characters per message. Reply drafting sends up to three chronological thread messages ending at the selected message, with at most 4,000 plain-text characters each (12,000 total), the user's intended answer or acknowledgment-only choice, selected tone, and reply metadata to the chosen drafting provider. Extract plain-text MIME parts and skip attachment parts; do not use HTML or separately download attachments as model input. A full-message Gmail response may contain other MIME parts that are not passed to models. Name the selected provider and show its data-transfer disclosure beside the inbox/chart before the student opens the live inbox. Show the exact bounded reply thread text and drafting provider before the student chooses **Generate reply**; that click initiates the drafting call. There is no live model call in sample mode.
- Sorting processes at most 15 eligible newest-window messages and 30 total model attempts including retries. Its ten-minute processing deadline starts before sequential body preparation; it prevents subsequent model/label work but does not abort preparation or an in-flight call. Cancel remaining work is offered during processing after preparation; remaining calls stop, completed labels remain, and unprocessed items are marked. A reply run permits at most three drafting-model attempts for the selected message, including student-requested redrafts; afterward an existing draft remains editable. Open pending replies resumes saved context without new Gmail retrieval. Generate another reply reuses that snapshot and remaining attempt budget. Interrupted sorts do not automatically resume, and unfinished sends become unknown after restart.
- Before live Gmail data is sent to either model provider, verify the provider's current data-use and retention terms against Google's Workspace API Limited Use requirements, document the decision, and give the student clear in-app disclosure. The providers may process data for this student's requested feature; Gmail data must not be used to train a general model through this app. If the terms or account configuration do not support that boundary, keep live model processing disabled until a compliant route is selected and approved.
- Treat mail contents and model outputs as untrusted data. They cannot ask the app to reveal credentials, call new tools, change labels outside this app's namespace, add recipients, or bypass approval.

## Gmail

- Use installed-app OAuth with the student's own Google account. The planned scope is `https://www.googleapis.com/auth/gmail.modify`, needed for reading and applying labels and documented by Google as also allowing compose/send. Request no full-mailbox `https://mail.google.com/` scope. Confirm scope behavior and any Google verification requirements during the Build Agent tool-plan stage.
- App-owned labels are created only as needed. `messages.modify` adds one `Student/` label and removes only a prior app-owned category label on the same message. It never changes `INBOX`, `UNREAD`, or Gmail's category labels. Ownership is established by recorded label IDs, not the Student/ prefix alone. A preexisting same-name label or a renamed/deleted owned label blocks labeling. A saved correction preserved in a later sort receives no fresh Gmail write or verification.
- Sending uses Gmail `messages.send` with a MIME reply to a user-selected incoming inbox message. The backend parses valid mailbox addresses from that message's Reply-To or From header. It displays the derived single recipient; if Reply-To contains multiple valid addresses, the user must choose exactly one in the app. Invalid or self-recipient addresses block sending; a `no-reply` address prompts a warning. The chosen address is bound to the one-use send authorization, which becomes invalid if the choice changes. Require a valid original Message-ID for live sending and preserve reply threading headers. No CC, BCC, forwarding, or attachment sending in this version.
- Each approved send uses one local operation ID, exact draft revision, and unique outbound Message-ID. If Gmail's response is lost, inspect local state and the Gmail Sent record before any user-initiated recovery. Never resend an uncertain operation from that run. Check Gmail Sent again performs only bounded reads. A successful response containing a message ID and matching thread is sent evidence; a definite failure permits fresh H2 review and confirmation. Send this reply only opens the final dialog; Confirm and send once creates the authorization and starts sending.

## Models

- Select the sorting model during the Build Agent model-choice stage. Verify its callable model ID, actual input/output format, access, cost, and ability to produce one of the five categories, an uncertainty/review signal, and a separate urgency estimate. Normalize and validate outputs in the local controller. If it offers meaningful category probabilities, the interface may show them as optional confidence bars. Reject unsupported categories or malformed responses, and show invalid urgency as unavailable. A provider outage creates an error/review status, never a fabricated category or score.
- Select the reply-drafting model during the same stage. Verify its callable ID and ability to return editable reply text plus missing-fact questions or placeholders. It has no Gmail tool permission and must not invent commitments, dates, qualifications, or attachments. Missing facts appear as visible placeholders or a student question. The app must support the chosen provider's data-use and retention terms before live Gmail text is sent.
- API credentials and usage are separate from Codex/ChatGPT subscriptions. Build with synthetic fixtures first, then perform only the approved connection tests and student-authorized live processing.
